# 托盘右键菜单重设计 Design Gate

状态：设计评审通过后实施
审查日期：2026-09-18

## Existing Design

托盘图标和菜单入口集中在 `src/app/tray_application.cpp`。`Shell_NotifyIconW` 注册通知区域图标，回调消息为 `WM_APP + 1`；左键打开快速启动菜单，右键和 `WM_CONTEXTMENU` 打开管理菜单。管理菜单由 `show_context_menu()` 使用原生 `HMENU`、`AppendMenuW` 和 `TrackPopupMenu` 动态创建，命令仍通过现有 `WM_COMMAND` 分发。

当前结构：

```text
托盘右键菜单
├─ 设置...
├────────
├─ 编辑菜单 >
│  ├─ 编辑主菜单
│  └─ 编辑第二菜单
├────────
├─ 语言 >
│  ├─ 简体中文
│  ├─ 繁體中文
│  └─ English
├────────
├─ 维护 >
│  ├─ 刷新菜单
│  ├────────
│  ├─ 打开 Everything
│  └─ 安装/修复 Everything 服务...
├────────
├─ 关于 简驭 | Simpilot
└─ 退出
```

当前菜单使用系统菜单绘制和系统键盘导航；快速启动菜单另有 `LaunchMenuRenderer` owner-draw 实现，提供 DPI、深色和高对比度处理。管理菜单没有自定义图标或自绘项目。

## UX Audit

### P1

问题：管理菜单固定使用 `TPM_BOTTOMALIGN | TPM_LEFTALIGN`。
原因：`track_menu()` 只为快速启动菜单计算工作区方向。
用户影响：任务栏位于屏幕顶部、侧边或多显示器边缘时，菜单可能向屏幕外展开或遮挡托盘位置。
建议：管理菜单也根据托盘点、当前显示器工作区和菜单尺寸选择上下、左右对齐；保留原生 `HMENU`。

问题：右键管理菜单与左键快速启动菜单的视觉处理不完全一致。
原因：两者使用不同的渲染路径，右键菜单依赖系统菜单主题。
用户影响：用户可能感知到主题和间距变化。
建议：先统一结构、分组和弹出行为；不引入自定义 Popup Window。系统菜单在深色、浅色、高对比度和屏幕阅读器场景下风险最低。

### P2

问题：一级菜单包含设置、编辑菜单、语言、维护、关于、退出六类内容。
原因：语言和维护是低频入口，但各自需要独立子菜单。
用户影响：总体可扫描，但低频内容会分散主要动作注意力。
建议：设置保持首项；将直接编辑配置文件的入口集中到“编辑菜单”二级入口；语言与维护继续使用二级入口，关于和退出固定底部；不把 Everything 维护动作提升到一级。

问题：编辑入口与设置中的可视化菜单编辑器容易被用户理解为同一个功能。
原因：两者都涉及主菜单和第二菜单，但一个编辑配置文本，一个编辑结构化项目。
用户影响：用户可能误以为文本编辑器保存后不会刷新，或在错误的工具中修改配置。
建议：菜单命名明确使用“编辑菜单”，子项使用“编辑主菜单/编辑第二菜单”；打开后交给 Windows 默认文档编辑器，并在用户手册中说明设置页仍是推荐的可视化编辑入口。

问题：维护子菜单同时包含刷新、Everything 和服务修复。
原因：这些都是运行维护而非日常动作。
用户影响：普通用户可能不理解“刷新菜单”的具体范围。
建议：保留短名称以符合原生菜单密度，详细含义放在用户文档；不可用 Everything 继续灰显。

### P3

问题：管理菜单没有访问键提示或图标。
原因：当前本地化文本没有统一 access key 规则，系统菜单也不要求图标。
用户影响：托盘菜单使用频率较低，影响有限。
建议：本次不新增可能冲突的访问键；不为现代感强行添加彩色图标。

## Problems

| 优先级 | 问题 | 原因 | 用户影响 | 建议 |
| --- | --- | --- | --- | --- |
| P1 | 菜单方向只按固定左上角策略弹出 | 管理菜单没有复用快速菜单的工作区方向判断 | 任务栏位于屏幕顶部、侧边或副屏边缘时，菜单可能贴边、遮挡或部分离屏 | 对管理菜单采用同一套基于光标、工作区和菜单尺寸的对齐策略 |
| P1 | 右键回调同时接受 `WM_RBUTTONUP` 与 `WM_CONTEXTMENU` | 托盘消息在不同 Windows 版本或鼠标驱动下可能同时到达 | 快速连续右键时可能重复打开或菜单重入 | 保留两条兼容路径，以 `menu_active_` 和单次消息验证确保一次手势只弹出一次 |
| P2 | 维护动作的语义不够显式 | “刷新菜单”既是配置刷新又可能触发 Everything 状态重新评估 | 新用户难以判断该项会影响什么 | 保持短命名，详情放入用户手册；不新增解释性菜单项 |
| P2 | 关于与退出缺少明确的低频分组 | 两者当前连续排列 | 用户扫视时容易把退出误认为普通动作 | 在关于与退出之间加入分隔线，退出保持最后一项 |
| P2 | 未定义本地化 Access Key 策略 | 三种内置语言和外部语言可能产生冲突 | 键盘用户缺少一致规则 | 本次不强行添加字母助记键；后续若引入，必须由语言资源显式提供并做冲突检查 |
| P3 | 管理菜单没有自定义图标和精细间距 | 使用系统 `HMENU` 绘制 | 与快捷启动菜单相比视觉控制较少 | 接受系统菜单的间距、圆角、阴影和无障碍优势，不为装饰引入 owner-draw |

## User Task Analysis

托盘右键菜单的主要任务按预期频率排序如下：

1. 打开设置：首次配置和偶发调整，必须在一级菜单首项一次点击可达。
2. 切换语言：低频、明确的偏好设置，适合保持为带 radio 状态的二级菜单。
3. 维护菜单或 Everything：故障排查和环境维护，低频且不应挤占一级动作区。
4. 查看关于：版本、许可和支持信息，低频信息任务，放在底部信息区。
5. 退出：终止托盘进程，低频动作，固定在最底部并与关于分隔。

用户打开菜单后的首要识别线索应是“设置、编辑菜单、语言、维护”四个不同语义的动作组；状态只通过 radio 或 disabled 表达，不再增加常驻状态说明行。

## Design Goals

- 让设置在一次点击内可达，维护和语言可发现但不抢占注意力。
- 让需要直接检查或修改配置文件的用户在两次点击内进入对应文件；不把文本编辑能力伪装成新的设置页面。
- 保留 Windows 原生菜单的上下方向键、左右展开、Enter、Esc、灰显和高对比度行为。
- 修正任务栏顶部、侧边、屏幕边缘和多显示器场景的弹出方向。
- 不改变现有 Command ID、`WM_COMMAND` 分发、配置格式或第三方依赖。
- 使用系统主题能力，避免硬编码颜色和大型 UI 框架。

## Option A: Windows Native

继续使用 `HMENU` 和 `TrackPopupMenu`，只调整结构和弹出定位。优点是开发和维护成本最低，键盘导航、无障碍、高 DPI 和高对比度风险最低；缺点是间距和图标控制受系统限制。适合本项目的默认基线。

## Option B: Modern Windows

保留 `HMENU`，为管理菜单增加有限的 owner-draw 项目、单色图标和自定义 padding。视觉可与快速启动菜单更接近，但需要维护 `WM_MEASUREITEM`、`WM_DRAWITEM`、子菜单数据所有权和高对比度逻辑，且系统辅助功能验证成本显著增加。

## Option C: Productivity / Power User

把“刷新菜单”提升为一级菜单并增加访问键或快捷提示。熟练用户操作更快，但一级项目更多，维护动作更突出，普通用户误触和认知负担更高。

## Design Review

| 维度 | A Native | B Modern | C Power User |
| --- | --- | --- | --- |
| 信息架构 | 清晰 | 清晰 | 更紧凑但更拥挤 |
| 操作效率 | 高 | 高 | 熟练用户最高 |
| 学习成本 | 最低 | 低 | 中 |
| Windows 一致性 | 最佳 | 良好 | 良好 |
| 视觉品质 | 系统依赖 | 较高 | 中 |
| 开发复杂度 | 低 | 中高 | 中 |
| 维护成本 | 低 | 高 | 中 |
| Bug/DPI/无障碍风险 | 最低 | 中高 | 中 |

## Final Proposal

采用 A 的原生交互基础与 B 的结构化分组，暂不采用 owner-draw 管理菜单，也不引入自定义弹窗。具体实现：

1. 保留现有命令 ID、原生 `HMENU`、`TrackPopupMenu` 和 `WM_COMMAND`。
2. 管理菜单结构使用“设置、编辑菜单、语言、维护、关于、退出”的层级，退出单独置底。
3. “编辑菜单”子项通过 Windows 默认文档编辑器打开 `Simpilot.ini` 或 `Simpilot2.ini`；第二菜单文件不存在时，先确认是否创建。
4. 管理菜单根据托盘点和显示器工作区计算对齐方向；快速启动菜单继续使用现有测量逻辑。
5. 继续通过 `MenuThemeController` 应用系统/浅色/深色菜单主题；高对比度由系统菜单负责。
6. 不新增图标、快捷键提示或复杂状态文本，避免本地化和无障碍回归。

### Rationale

推荐方案不是追求最强视觉定制，而是把现有菜单的结构、弹出位置和低频操作分组修正到稳定状态。原生 `HMENU` 已经提供 Windows 用户期待的焦点、键盘导航、子菜单和辅助功能语义；当前最大的体验风险来自信息分组和屏幕边界，而不是缺少圆角或图标。

## Menu Structure

```text
设置...
────────
编辑菜单 >
├─ 编辑主菜单
└─ 编辑第二菜单
────────
语言 >
维护 >
────────
关于 简驭 | Simpilot
退出
```

语言子菜单使用 radio checked 表示当前语言。维护子菜单使用 disabled 表示 Everything 组件不可用；编辑菜单子项始终可见，第二菜单文件不存在时选择该项会先请求创建确认；不增加独立状态项。

## Interaction Spec

- 左键、右键、`WM_CONTEXTMENU` 均沿用现有托盘入口。
- `SetForegroundWindow` 后调用 `TrackPopupMenu`，菜单结束后发送 `WM_NULL`，避免菜单无法正确关闭。
- Up/Down 移动项目，Right 展开子菜单，Left 返回父菜单，Enter 执行，Esc 关闭。
- 选择设置时沿用现有 `settings_pending_`，避免菜单回调中直接销毁父窗口。
- 选择“编辑主菜单/编辑第二菜单”时，使用文件关联打开配置文件；第二菜单文件缺失时先显示可取消的创建确认，不因取消而创建空文件。
- 外部编辑器保存后沿用配置监视器自动刷新；解析失败不替换当前有效菜单。
- 菜单打开方向由当前托盘点、显示器 `rcWork` 和估算菜单尺寸共同决定；不能依赖主显示器坐标。

## Visual Spec

管理菜单使用系统菜单字体、系统颜色和系统缩放，不写死像素。深色主题由 `MenuThemeController` 控制；浅色/跟随 Windows/高对比度使用系统颜色。分隔线仅用于“设置”和低频语言/维护区与底部关于/退出区之间的分组。圆角、阴影、图标和自定义颜色不在本次范围内，以避免破坏系统一致性。

尺寸要求采用系统菜单度量，不写死物理像素。Windows 负责将菜单字体、项目高度、分隔线、子菜单箭头和屏幕边界按当前线程 DPI 缩放；验收需覆盖 100%、125%、150%、175% 和 200%。

## Accessibility

优先保持原生菜单：支持键盘导航、Esc、Enter、左右子菜单、屏幕阅读器的菜单语义、高对比度颜色、系统字体和 100%～200% DPI。测试需覆盖 Windows 10/11、浅色/深色/高对比度、单/双显示器及不同 DPI。

## Technical Approach

在 `TrayApplication::track_menu()` 中复用现有 `launch_menu_alignment()` 的方向判断。对管理菜单先使用系统菜单尺寸查询；若无法可靠取得尺寸，则以系统菜单默认尺寸结合工作区边界做保守的上下选择。编辑动作使用 Windows 文件关联（默认文档编辑器），不要把管理菜单接入 `LaunchMenuRenderer`，避免 owner-draw 生命周期、子菜单 item data 和无障碍回归。

技术约束：

- 不修改现有 Command ID 和 `WM_COMMAND` 分发协议。
- 不把 `HMENU` 生命周期交给静态全局对象；父菜单销毁前先销毁子菜单或依赖 Windows 的父菜单销毁语义并在验证中确认。
- `SetForegroundWindow`、`TrackPopupMenu`、`WM_NULL` 收尾顺序保持不变，避免菜单关闭后焦点残留。
- 任何定位改动都必须使用虚拟屏幕坐标和 `MonitorFromPoint`，不得假设主显示器原点为 `(0, 0)`。

## Implementation Plan

1. 增加原生菜单尺寸估算/对齐辅助函数，处理上下左右工作区边界。
2. 在 `show_context_menu()` 保持现有菜单树和命令 ID，只整理构建顺序与注释。
3. 运行现有单元测试和 `git diff --check`，进行 Windows Debug/Release 构建。
4. 人工验证任务栏顶部/底部/侧边、多显示器、浅色/深色/高对比度和键盘导航。

## Test Plan

- 编译：Debug、Release。
- 功能：设置、编辑主菜单、编辑第二菜单（含缺失文件确认）、语言 radio、刷新、Everything 灰显/可用、关于、退出。
- 编辑器保存有效配置后验证自动刷新；保存无效配置后验证上一份有效菜单仍保持活动。
- 交互：左键/右键、Enter、Esc、上下左右键、菜单快速连续打开。
- 环境：Windows 10/11，100%、125%、150%、200%，单/双显示器，不同 DPI。
- 回归：Explorer 重启后托盘图标重建，菜单主题恢复，菜单句柄和图标无泄漏。
